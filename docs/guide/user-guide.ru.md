# Sorta — Руководство пользователя (русский)

> Языки: [English](user-guide.en.md) · **Русский** · [日本語](user-guide.ja.md)

Sorta — инструмент командной строки и локального веб‑интерфейса, который
**индексирует большую коллекцию фото/видео** (протестировано на 60+ ГБ, рассчитано
на 300+ ГБ) и **раскладывает файлы в новую структуру папок** — по **городам/странам**,
по **людям** или по **событиям** — с полными гарантиями безопасности (по умолчанию
dry‑run, журнал перемещений и откат одной командой).

- **Локально по умолчанию.** Все ML‑модели (лица, определение сцен/текста) работают
  офлайн на вашей машине (рекомендуется GPU). Ничего не отправляется наружу, пока вы
  явно не включите онлайн‑провайдер в конфиге.
- **Оригиналы никогда не изменяются.** Сортировка *перемещает* или *копирует* файлы;
  EXIF не переписывается. С `--copy`/`--link` оригиналы остаются на месте.
- **Два способа работы:** пошаговый **веб‑интерфейс** (`sorta ui`) или **CLI**. Оба —
  обёртки над одним движком, выбирайте удобный.

## 2. Требования

| Компонент | Требование |
|---|---|
| ОС | Windows, Linux или macOS |
| Python | 3.11 – 3.14 (`requires-python >=3.11,<3.15`) |
| Менеджер окружения | [`uv`](https://docs.astral.sh/uv/) (рекомендуется) или `pip` |
| `exiftool` | **Обязателен** для метаданных HEIC/RAW/видео (даты, GPS, ориентация) — по сути, любое фото с современного телефона. Без него Sorta откатывается на Pillow, которая читает только JPEG/PNG/TIFF/WEBP и не читает видео. |
| Место на диске | Достаточно для новой структуры. `--copy` дублирует данные (×N). `--link` (жёсткие ссылки) почти не занимает места (тот же том, NTFS/ext4/APFS). Плюс SQLite‑индекс и (опционально) миниатюры — оба малы относительно самой коллекции. |

ML‑бэкенд Sorta (лица, CLIP/OCR для классификации мусора) ставится через один из
двух **взаимоисключающих установочных профилей** — выберите под своё железо:

| | Профиль CPU (экстра `cpu`) | Профиль GPU (экстра `gpu`) |
|---|---|---|
| Железо | Любая машина x86‑64, GPU не нужен | NVIDIA GPU + драйвер с поддержкой **CUDA 13** (проверено на Blackwell/RTX 5090) |
| Бэкенд | `onnxruntime` (CPU) + CPU‑сборки torch/torchvision | `onnxruntime-gpu` + рантайм CUDA 13/cuDNN 9 (pip‑wheels) + CUDA‑сборки torch/torchvision |
| Скорость лиц/CLIP | Работает корректно, но **медленно** — на большой коллекции `faces`/`junk`/`landmarks` займут часы. Хватает для раскладки по городам + дублей (лица/события всё равно opt‑in, см. §8), пригодно для небольших коллекций с включёнными лицами/событиями. | Быстро. Замер 28.07.2026 на коллекции из 24 196 фото, лица+события+junk включены: **≈ 40 мин** на полный прогон без глубокого яруса. Опциональный глубокий VLM‑ярус (`vlm.enabled` / `uv sync --extra vlm`) добавляет **+122 мин**, но разово — разбивка по этапам в §8. |
| RAM | Рекомендуется 8 ГБ+ (индексация/хэширование — самая RAM‑затратная часть, не зависит от профиля) | То же, плюс сколько зарезервирует драйвер GPU |
| VRAM | н/д | **~3 ГБ** для базы + лиц (замерено на RTX 5090: CLIP ViT‑L ≈2.0 ГБ + buffalo_l ≈0.6 ГБ) — комфортно на GPU с **≥4 ГБ**. Опциональный глубокий VLM‑ярус (Qwen2.5‑VL‑3B) добавляет ≈7 ГБ (оценка по 3B fp16, не замерено) → **≥8 ГБ** суммарно |

Тайминги и VRAM — наблюдения с нашего железа, не гарантия — на вашем результат
зависит от состава коллекции (видео‑превью, RAW, число лиц на фото — основные
факторы стоимости).

## 3. Установка

### 3.1 Перед установкой

```bash
git clone https://github.com/shinKatana0/sorta.git
cd sorta

# Установить exiftool — ОБЯЗАТЕЛЕН для метаданных HEIC/RAW/видео:
#   Windows: winget install OliverBetz.ExifTool
#   Debian/Ubuntu: sudo apt install libimage-exiftool-perl
#   macOS: brew install exiftool

# Создать свой конфиг из шаблона
cp config.example.yaml config.yaml
```

Без `exiftool` Sorta откатывается на Pillow: только JPEG/PNG/TIFF/WEBP, видео не
читается совсем, а у HEIC/RAW не будет дат, GPS и ориентации. На телефонной
коллекции это почти все метаданные, по которым Sorta и раскладывает файлы, — так что
это требование, а не пожелание.

### 3.2 Выбор профиля под железо

ML‑бэкенду Sorta (лица, CLIP/OCR) нужен ровно один профиль. `cpu` и `gpu` —
**взаимоисключающие** экстры (`tool.uv.conflicts` в `pyproject.toml`): ставится
ровно один, никогда оба. Что реально приезжает с каждой комбинацией (проверено
резолвом `uv pip compile` 2026‑07‑26):

| Экстра | Что ставится |
|---|---|
| `cpu` | `torch==2.13.0+cpu`, `onnxruntime` |
| `gpu` | `torch==2.13.0+cu130`, `onnxruntime-gpu` |
| `gpu,vlm` | набор `gpu` + `transformers==4.51.3` |
| `cpu,vlm` | набор `cpu` + `transformers==4.51.3` |

`vlm` — опциональный глубокий VLM‑ярус классификации (`vlm.enabled` /
`--deep`, см. §8); без него этот ярус молча откатывается на быстрый CLIP‑ярус.
`dev` добавляет инструменты гейта (ruff, mypy, pytest) — нужны только для
`scripts/check.py` и тестов.

### 3.3 Установка команды `sorta` (`uv tool install`)

> **У `uv tool install` НЕТ флага `--extra`.** Экстра задаётся *внутри спецификации
> пакета*, в том же закавыченном аргументе, что и путь:
> `uv tool install "C:\path\to\sorta[gpu]"`. Именно на этом встал живой сценарий:
> команду запустили без экстры, она собрала обычный пакет — то есть **CPU‑профиль**,
> и torch приехал `+cpu` на машине с нормальной видеокартой.

```bash
# только CPU
uv tool install "C:\path\to\sorta[cpu]"

# GPU (NVIDIA / CUDA 13)
uv tool install "C:\path\to\sorta[gpu]"

# GPU + глубокий VLM‑ярус
uv tool install "C:\path\to\sorta[gpu,vlm]"

# CPU + глубокий VLM‑ярус
uv tool install "C:\path\to\sorta[cpu,vlm]"

# …любой из них в editable‑режиме, для локальных правок кода
uv tool install -e "C:\path\to\sorta[gpu]"
```

`C:\path\to\sorta` — ваш чекаут; если вы уже внутри него, работает `.`
(`uv tool install ".[gpu]"`). Аргумент всегда закавычивайте: неэкранированные
`[...]` в большинстве шеллов — это glob.

- **`-e` нужен, если собираетесь править код.** Без него установка — снапшот:
  меняете файл, запускаете `sorta` и получаете поведение старой копии, причём на
  экране нет ни одного намёка почему. С `-e` правки видны сразу, и забывать про
  переустановку становится нечего.
- **Смена профиля или обновление не‑editable установки после `git pull`** —
  переустановка с `--force` и нужной экстрой:
  `uv tool install --force "C:\path\to\sorta[gpu]"`.
- Когда Sorta будет опубликована на PyPI, та же форма станет
  `uv tool install "sorta[gpu]"` — без локального чекаута.

Это резолвит ту же схему профилей/индексов из `pyproject.toml` (индексы
`pytorch-cu130` / `pytorch-cpu`), что и `uv sync`, и ставит команду `sorta` на
PATH: дальше запускайте `sorta ui`, `sorta index …` и остальное из любого
терминала, из любой папки — без `uv run`, без активного venv.

### 3.4 Окружение для разработки (`uv sync`)

```bash
uv sync --extra gpu --extra dev      # NVIDIA GPU + драйвер CUDA 13
# или
uv sync --extra cpu --extra dev      # без NVIDIA GPU

# Активировать один раз на сессию терминала:
.\.venv\Scripts\Activate.ps1         # Windows PowerShell
source .venv/bin/activate            # Linux/macOS/bash
```

Именно `uv sync` принимает `--extra` как флаг, и профиль ему нужен так же явно:
указывайте `--extra cpu` или `--extra gpu` сами — за вас никто не выберет.
GPU‑wheels тянут рантайм CUDA 13 обычными pip‑пакетами, системный CUDA Toolkit не
нужен. С активным venv `sorta …` запускается прямо из вашего чекаута, и правки кода
видны сразу.

> **Не запускайте `uv run sorta …` как повседневную команду.** `uv run <cmd>`
> перед каждым запуском пересинхронизирует окружение под базовый набор
> зависимостей из `pyproject.toml` — если не повторять `--extra <профиль>`
> на этой самой команде каждый раз, пересинк молча роняет GPU‑пакеты (torch
> откатывается на CPU‑сборку) при каждом запуске. Установка через `uv tool install`
> (§3.3) и активированный venv полностью обходят эту проблему — в этом и весь
> смысл поставить один раз вместо запуска через `uv run`.

### 3.5 Сразу после установки — `sorta doctor`

`sorta doctor` — первая команда после установки. Она не трогает базу и ничего не
качает, а просто показывает, чем на самом деле оказалась установка:

```
$ sorta doctor
torch: 2.13.0+cu130 (CUDA available: yes, device: NVIDIA GeForce RTX 5090 Laptop GPU)
onnxruntime providers: TensorrtExecutionProvider, CUDAExecutionProvider, CPUExecutionProvider (CUDA: yes)
mismatch: no
geo data: C:\...\sorta\data\geo\places.tsv (9.2 MB)
Лог прогона: C:\Users\you\AppData\Local\sorta\logs\sorta.log
Кэш превью: C:\Users\you\AppData\Local\sorta\previews
```

Как читать построчно:

- **`torch: … (CUDA available: yes|no)`** — какая сборка в итоге встала. На профиле
  `gpu` здесь должно быть `+cu130` и `CUDA available: yes`. Сборка `+cpu` означает,
  что экстра не доехала до команды установки (§3.3).
- **`onnxruntime providers: …`** — на чём может работать детекция лиц. Есть
  `CUDAExecutionProvider` — GPU ей доступен; нет — лица считаются на CPU (§3.6).
- **`mismatch: yes`** — torch собран без CUDA, а у onnxruntime CUDA есть. Тогда лица
  идут на GPU, а CLIP и OCR тихо считаются на CPU: это и есть тот медленный
  молчаливый провал, ради которого строка существует.
- **`geo data: …places.tsv (N MB)`** — встроенная база GeoNames, по которой
  раскладка по городам резолвит координаты. Файл должен существовать и быть
  непустым; если строка помечена `⚠` и говорит FILE NOT FOUND / FILE IS EMPTY, то
  каждая координата резолвится в пустое место, а лечится это переустановкой (или
  `python scripts/build_geodata.py` в чекауте).
- **`Лог прогона:`** — куда пишется лог прогона (§19).
- **`Кэш превью:`** — где лежит кэш превью (§18); суффикс ` (ОТКЛЮЧЁН)` означает,
  что кэш выключен.

Пример снят с `language: ru`; две первые сводки (`torch`/`onnxruntime` и `geo data`)
приходят из модуля диагностики и остаются английскими при любом `language`, а строки
про лог и кэш переводятся. `config.yaml` эта команда читает только чтобы узнать язык
вывода — без него она тоже работает, просто печатает на языке по умолчанию, — поэтому
путь кэша показывается дефолтный плюс то, что задано переменной `SORTA_PREVIEW_DIR`.

### 3.6 Известная ловушка: `onnxruntime` затирает `onnxruntime-gpu`

`insightface` (детекция лиц) зависит от обычного пакета `onnxruntime`, а экстра
`gpu` ставит `onnxruntime-gpu`. Это два разных дистрибутива, которые
распаковываются в один и тот же каталог `onnxruntime` — кто встал последним, тот и
победил. Если последним оказался CPU‑пакет, лица молча уезжают на CPU, и нигде
никакой ошибки.

Признак виден в `sorta doctor`: в списке провайдеров **нет**
`CUDAExecutionProvider`, например:

```
onnxruntime providers: AzureExecutionProvider, CPUExecutionProvider (CUDA: no)
```

Обход — переустановить GPU‑пакет поверх, не давая pip заново разрешать
зависимости:

```bash
python -m pip install --force-reinstall --no-deps onnxruntime-gpu
```

`--no-deps` тут обязателен: без него pip заново резолвит `insightface` и снова
притаскивает CPU‑версию `onnxruntime`. Запускать нужно в том окружении, куда
установлена Sorta (в активированном venv проекта), после чего повторить
`sorta doctor` и убедиться, что `CUDAExecutionProvider` вернулся в список.

## 4. Настройка

Sorta читает `config.yaml` (скопируйте из `config.example.yaml`). Два обязательных к
проверке параметра:

```yaml
sources:
  - "D:/Photos"          # папка(и) с фото/видео (сканируются рекурсивно)
database: "sorta.db"     # где хранится SQLite‑индекс
language: ru             # язык интерфейса/папок: ru | en | ja  (по умолчанию en)
```

- **`sources`** — одна или несколько корневых папок для сканирования. Путь можно также
  передать в командной строке (`sorta index /путь/к/фото`) — он переопределяет конфиг.
- **`language`** — задаёт язык генерируемых **имён папок** (напр. `Россия/…` vs
  `Russia/…`), **хрома веб‑интерфейса** и **консольных сообщений CLI**.
  Поддерживаются: `ru`, `en`, `ja`. Ключа нет в конфиге — язык `en`.

> **Замечание:** одно исключение — тексты `--help`. Они живут в декораторах typer и
> вычисляются при импорте модуля, ещё до чтения конфига, поэтому `sorta --help` и
> `sorta sort --help` остаются на английском при любом `language`. Всё остальное —
> имена папок, веб‑интерфейс, строки прогресса и итоговые сводки команд —
> локализовано. Как выглядит реальный вывод CLI — см. примеры в §7 и §9, а если он
> превращается в `????` в терминале — см. §22.

Все параметры — в разделе [Справочник конфигурации](#21-справочник-конфигурации).

## 5. Ключевые понятия

**Индекс отделён от сортировки.** Сначала пайплайн наполняет SQLite‑**индекс**
(метаданные, гео, эмбеддинги лиц, кластеры, события, junk‑классификация). Сортировка —
это лишь *применение представления* индекса к файловой системе. Смена режима
(город ↔ люди ↔ события) **не** требует пересканирования.

**Dry‑run по умолчанию.** `sort` и `album` печатают план и ничего не пишут, пока вы не
добавите `--apply`. Всегда сначала смотрите план.

**Журнал и откат.** Каждое перемещение/копирование/линк записывается в журнал *до*
операции с ФС; `sorta undo` откатывает последний батч. Хэши (blake3) сверяются перед
перемещением; конфликт имён → суффикс `_1`, `_2` — существующий файл никогда не
перезаписывается.

**Три режима переноса.**
- **move** (по умолчанию для `sort`) — перемещает файл. Одна структура на диске.
- **copy** — дублирует файл; оригиналы не тронуты. Возможно несколько структур, ×N
  места.
- **link** (hardlink, по умолчанию для `album`) — второе имя тех же байтов; почти ноль
  лишнего места; фолбэк на copy при переносе между томами/ФС.

**Канон + альбомы.** Рекомендуемая модель: одна **каноническая** структура по городам,
плюс **альбомы по запросу** (конкретный человек / событие), собираемые в отдельные
именованные папки жёсткими ссылками.

## 6. Быстрый старт — веб-интерфейс (рекомендуется)

Веб‑интерфейс — самый простой путь, из терминала нужен только запуск.

```bash
sorta ui                       # локальный сервер на http://127.0.0.1:8756
```

Далее в браузере:

1. Вкладка **Обзор** → состояние коллекции одним экраном: сколько файлов в индексе,
   фото и видео, дубликаты, ошибки чтения, события; откуда взялось место (точный GPS,
   указано вручную, унаследовано от съёмки/поездки/имени папки, определено по кадру) и
   сколько кадров без места вообще; что показал разбор (личные фото, товары, документы,
   скриншоты, мемы — чем и каким ярусом решено); была ли уже раскладка, куда, в каком
   режиме и сколько файлов доехало. Числа **кликабельны**: клик уводит на вкладку, где
   с этой группой можно что-то сделать. Видна всегда; на пустом индексе показывает
   кнопку **К обработке**.
2. Вкладка **Обработать** → укажите путь к папке с фото. Два чекбокса, по умолчанию
   **выключены**: **«Разбор по лицам»** и **«Разбор по событиям»** — самые долгие
   этапы пайплайна, opt‑in намеренно (см. §8). Оставьте их выключенными для быстрого
   прогона только по городам, либо включите нужное. Нажмите **Обработать**: пайплайн
   идёт в фоне с прогрессом по этапам (индекс → гео → landmarks → [лица] → [события]
   → junk → почти‑дубли — лица/события только если включены). Вкладку можно
   закрыть — обработка продолжится.
3. Вкладка **Города** → посмотрите предлагаемую структуру (`Страна/Город/Год/Район`).
   Здесь же — колонка **Настройки** (см. ниже) и кнопка запуска раскладки.
   Видна всегда.
4. Вкладка **Дубли** → разберите группы почти‑дубликатов; рекомендованный кадр (★)
   выбран заранее. Поправьте, где не согласны, и один раз нажмите **Сохранить весь
   выбор**. Видна всегда.
5. Вкладка **Люди** → появляется только когда есть кластеры лиц (вы хоть раз включали
   «Разбор по лицам» или запускали `sorta faces`). Назовите кластеры и слейте дубли
   одного человека.
6. Вкладка **События** → появляется только когда есть события (вы хоть раз включали
   «Разбор по событиям» или запускали `sorta events`). Переименуйте события; соберите
   любого человека/событие в папку кнопкой **Собрать в папку**.
7. Вкладка **Не личные фото** → корзины того, что классификатор унёс из памяти:
   **Товары**, **Документы**, **Скриншоты**, **Мемы** (и «Все» разом). Отметьте кадры,
   попавшие сюда зря, и нажмите **Вернуть в фото** — они снова разложатся по городам;
   вердикт модели при этом не переписывается, а сам возврат откатывается кнопкой
   **Отменить возврат**. Видна всегда.
   **Документы показываются без миниатюр** — только имя файла и дата. Это правило, а
   не недоделка: в этой корзине лежат паспорта, справки и медицинские бланки, и Sorta
   не открывает и не рисует их даже локально; имени и даты хватает, чтобы решить
   судьбу кадра.
8. Вкладка **Перемещения** → после применения сортировки/альбома видно, что куда
   легло. Отсюда же раскладка **откатывается** (§15). Видна всегда.

На вкладке **Обработать** есть ещё два чекбокса, помимо лиц/событий, — оба
отражают `config.yaml` и работают как полный override только для этого прогона
(отметил = принудительно вкл, снял = принудительно выкл) — UI-эквивалент CLI-флагов
`--deep`/`--no-deep` и `--geo online`/`--geo offline` (§8):

- **«Глубокий анализ (VLM)»** — использовать глубокий VLM-ярус вместо быстрого
  CLIP-яруса для классификации junk/документов. Реально включается, только если
  он *одновременно* запрошен (этот чекбокс, `--deep`, либо
  `vlm.enabled: true` в конфиге) *и* установлен (extra `vlm`, например
  `uv tool install ".[gpu,vlm]"` или `uv sync --extra gpu --extra vlm --extra
  dev`) — без этого extra он молча откатывается на быстрый CLIP-ярус, о чём и
  говорит подсказка под чекбоксом.
- **«Онлайн-гео (точнее заграница)»** — использовать онлайн-геокодинг Nominatim
  вместо офлайн-данных GeoNames для этого прогона; отправляет только
  GPS-координаты, никогда не фото (см. §15).

Если после прогона «Люди»/«События» не появились — это ожидаемо: значит лица/события
не были включены для этого прогона, а не что-то сломалось; перезапустите с
включённым чекбоксом (или `sorta faces`/`sorta events`) — вкладка появится.

### Колонка «Настройки»

Справа на вкладке **Города** — колонка **Настройки**. Она меняет `config.yaml`
по-настоящему: значение сохраняется в файл сразу, **перезапускать `sorta ui` не
нужно** — следующий прогон читает уже новое. Что там есть:

- **Глубокий анализ (VLM)** — `vlm.enabled` (§21). В отличие от одноимённого чекбокса
  на вкладке «Обработать», который действует только на один прогон, тумблер здесь
  пишет значение в конфиг насовсем.
- **Модель**, **Потоки подготовки**, **Разрешение кадра, px** — `vlm.model`,
  `vlm.workers`, `vlm.max_edge`.
- **Качество кадра** — набор F113, по умолчанию выключенный. Сгруппирован по тому, ЧЕМ
  признак считается, потому что в этом вся разница в цене:
  - **Без VLM** — считается на проходе, который и так идёт: **Искать животных**
    (`features.pets`, порог `features.pet_threshold`) отвечает **CLIP**, а не модель,
    и работает даже при выключенном глубоком анализе; `features.sharpness_max_edge` —
    размер превью для резкости, а сама резкость это дисперсия лапласиана, вообще без
    модели.
  - **Через VLM** — **Спрашивать модель о качестве** (`vlm.quality`) и **У каких кадров
    спрашивать** (`vlm.quality_scope` — выпадающий список, потому что «Все кадры» стоит
    около 4 часов на коллекции в 20 тысяч). Нужен включённый `vlm.enabled` и экстра
    `vlm`.
  - **Кого спрашивать у модели** — два входа в дорогую часть: полоса неопределённости
    резкости (`features.sharpness_band_min` / `features.sharpness_band_max`) и
    `features.subject_score_min` — вероятность от CLIP, ниже которой он сам не понял,
    на что смотрит.
- **Потолок кэша превью, ГБ** — `imaging.preview_cache_max_gb` (§18).
- **Папки → Язык названий папок** — `language`. План раскладки ниже пересчитывается
  сразу, без перезапуска.

Во время прогона настройки не меняются: колонка сообщает, что идёт обработка, и просит
дождаться конца.

Сервер слушает только `127.0.0.1` (недоступен из сети). Остановка — `Ctrl+C`.

## 7. Быстрый старт — CLI

Примеры ниже предполагают, что `sorta` уже на PATH — через `uv tool install` или
активированный venv (§3). Не добавляйте перед ними `uv run` — почему, см.
предупреждение в §3.

```bash
# 1) Индексация папки (метаданные, хэши, точные дубли)
sorta index /путь/к/фото

# 2) Базовый пайплайн (гео, landmarks, junk) + хэши почти‑дублей — без лиц/событий
sorta run
sorta phash

# 2b) ...или включить ещё и лица/события (самые долгие этапы, см. §8):
sorta run --faces --events

# 3) Предпросмотр сортировки по городам (dry-run — CSV + HTML план, ничего не двигает)
sorta sort --by city --dest /путь/к/разложенному

# 4) Применить (copy неразрушающий; без --copy будет MOVE)
sorta sort --by city --dest /путь/к/разложенному --copy --apply

# Откат последнего батча при необходимости
sorta undo
```

## 8. Пайплайн обработки

`sorta run` (или кнопка **Обработать** в UI) выполняет этапы по порядку. Каждый —
отдельная команда, и все **инкрементальны** (повторный запуск обрабатывает только
новые/изменённые файлы):

| Этап | Команда | По умолчанию? | Что делает |
|---|---|---|---|
| Индекс | `sorta index [dir]` | всегда | Сканирует файлы, читает EXIF/даты, считает blake3, помечает точные дубли. |
| Гео | `sorta geo` | всегда | Определяет место по GPS; для файлов без GPS наследует место от соседей по времени, а затем от всей поездки, если её кадры с GPS согласны насчёт города и окружают файл по времени (офлайн GeoNames или онлайн Nominatim, если включён). |
| Landmarks | `sorta landmarks` | всегда | Визуальное определение места для сцен без GPS, консервативный порог — заполняет город, например, для фото достопримечательности в помещении без GPS. |
| Лица | `sorta faces` | **opt‑in** (`--faces`) | Детектирует лица (insightface), считает эмбеддинги, кластеризует людей (HDBSCAN). Самый долгий этап; пропускается, если явно не запрошен. |
| События | `sorta events` | **opt‑in** (`--events`) | Группирует фото в события по разрывам времени + городу; именует по дате + городу. Независим от лиц — включайте любое, оба или ни одного. |
| Junk | `sorta junk` | всегда | Классифицирует фото: `photo` / `screenshot` / `meme` / `document` / `product` (эвристики + CLIP + плотность текста). Класс `product` (товар, снятый на продажу) даёт только глубокий VLM‑ярус — быстрый ярус его не выдаёт вовсе, см. §14. |
| Хэши почти‑дублей | `sorta phash` | всегда (UI); в CLI отдельная команда (`sorta run` её не вызывает — гоняйте `sorta phash` сами) | Перцептивные хэши для почти‑дубликатов. |

**Флаги `sorta run`** (все опциональны, все — override только на ЭТОТ прогон,
в `config.yaml` ничего не пишется):

```
--faces / --no-faces       Детекция+кластеризация лиц в этом прогоне (по умолчанию: выкл)
--events / --no-events     Построение событий в этом прогоне (по умолчанию: выкл)
--deep / --no-deep         Глубокий VLM-ярус классификации junk в этом прогоне
                            (нужен `uv sync --extra vlm`; без него аккуратный откат
                            на быстрый CLIP-ярус). По умолчанию — из config.yaml
                            (vlm.enabled).
--geo offline|online       Провайдер геокодинга для этого прогона. `online` точнее
                            за границей, но отправляет GPS-координаты (не фото)
                            в Nominatim. По умолчанию — из config.yaml (geo.provider).
--by city|person|event     Дополнительно напечатать dry-run план сортировки в конце (§9)
--dest DIR                 Куда этот план (без него — in-place)
```

**Базовый прогон** (`sorta run` без флагов) намеренно быстрый путь: раскладка по
городам и поиск дублей, больше ничего. Включайте `--faces`/`--events`, когда
действительно нужна сортировка/альбомы по людям или событиям — отдельный последующий
запуск `sorta faces`/`sorta events` работает точно так же и в любом случае полностью
инкрементален. Покрытие в любой момент — `sorta stats`.

### Сколько это занимает

Замер 28.07.2026 на боевой коллекции из **24 196 фото** (RTX 5090, GPU‑профиль,
лица и события включены):

| Стадия | Время |
|---|---|
| `index` | 6,1 мин |
| `landmarks` | 2,8 мин |
| `faces` | 16,1 мин |
| `junk` (быстрый ярус) | 14,1 мин |
| `geo`, `events`, `phash` | секунды |
| **Полный прогон без глубокого яруса** | **≈ 40 мин** |
| Глубокий VLM‑ярус (7 896 кандидатов из 24 196) | **+122 мин, разово** |

«Разово» — не фигура речи: инкрементальность junk идёт по `media_class.tier`, поэтому
повторный прогон трогает только новые файлы, а уже размеченные глубоким ярусом кадры
второй раз в модель не отправляются. Первый прогон с `--deep` — это цена входа, а не
постоянный налог на каждую обработку.

Цифры — наблюдение с нашего железа, не гарантия: на вашем результат зависит от состава
коллекции (видео, RAW, число лиц на кадре — основные факторы стоимости).

## 9. Сортировка: города, люди, события

```bash
sorta sort --by city   --dest <dir> [--apply] [--copy|--move] [--where …] [--dedupe]
sorta sort --by person --dest <dir> [--apply] …
sorta sort --by event  --dest <dir> [--apply] …
```

- **`--by city`** → `Страна/Город/Год/Район/…` (локализованные имена).
- **`--by person`** → папка на каждого **названного** человека (сначала назовите
  кластеры — см. §11).
- **`--by event`** → `Год/ИмяСобытия/…`.
- **`--dest`** — целевой корень. Без него сортировка **in‑place** (реструктурирует
  саму исходную папку — dry‑run, журнал и undo всё равно действуют).
- **`--copy` / `--move`** — копировать (оригиналы сохраняются) или перемещать (по
  умолчанию).
- **`--where`** — фильтр плана, повторяемый: `--where "country=DE" --where "year>=2020"`.
- **`--dedupe`** — увести худшие почти‑дубли в папку `_Duplicates`.
- **`--exclude <path>`** — пропустить уже разобранную подпапку.

Файлы, не подходящие под режим, уходят в review‑папки: `_Неразобрано/` (нет места /
даты / junk), `_Документы/` и `_Товары/` (см. §14).

Без `--apply` — **dry‑run**: CSV + просматриваемый HTML‑план в `report_output/` рядом с базой, и
**ничего не перемещается**.

```
sorted_apply/_Неразобрано/мусор/screenshot/shot_01.jpg

$ sorta undo -c config.yaml
Откат батча 2: возвращено 12, отсутствовало 0, ошибок 0

$ find sorted_apply -type f
(ничего — undo убрал все копии)
```

На `language: ja` та же сортировка даёт `フランス/パリ/2023/…` и, что интересно,
`日本/東京都/2023/桜丘町/…` — подпапку **района** (Сакурагаока), которой нет для
`en`/`ru` на том же файле. Это не баг: в bundled‑данных GeoNames есть японские
локализованные имена районов, которых нет для `en`/`ru`, и
`naming.drop_unlocalized_district` (по умолчанию включён) скрывает сегмент района
для языка, на который его нельзя локализовать, вместо показа сырого
транслитерированного кода.

**Фильтрация через `--where`:**

```
$ sorta sort --by city --dest sorted_fr --where "country=FR" -c config.yaml
sort --by city (dry-run): 7 файлов -> 1 каталогов; план: …
```

В план попадают только 7 файлов, разрешённых во Францию; остальное вообще не входит
в план (не уходит в `_Неразобрано`).

### Пример — `--by event`

```
$ sorta sort --by event --dest sorted_event -c config.yaml
sort --by event (dry-run): 12 файлов -> 3 каталогов; план: …
```

| path | event | target |
|---|---|---|
| `paris_01.jpg` … `person_a_1.jpg` (7 файлов) | `2023-06-10..06-11 Paris` | `2023/2023-06-10..06-11 Paris/<имя>.jpg` |
| `tokyo_01.jpg`, `tokyo_02.jpg`, `tokyo_03.jpg`, `person_a_2.jpg` (4 файла) | *(нет — ниже `events.min_event_size`)* | `2023/11/<имя>.jpg` — резерв `no_event`, группировка по году/месяцу вместо этого |
| `shot_01.jpg` | | `_Неразобрано/мусор/screenshot/shot_01.jpg` — junk побеждает в любом режиме |

Это тот же порог `min_event_size` из §7/§12 в деле: у токийского дня были реальный
GPS, реальные метки времени, реальное место — всё, кроме *достаточного числа файлов*,
чтобы стать самостоятельным именованным событием.

### Пример — `--by person`

Режиму person нужны сначала **названные кластеры лиц** (§11), а для них — реальные
лица, которые `sorta faces` находит на настоящих фотографиях — то, что наши
синтетические заглушки честно продемонстрировать не могут (см. заметку в §7 и
оговорку в §11). После того как вы назвали пару кластеров на реальной коллекции,
это выглядит так:

```bash
sorta sort --by person --dest /путь/к/разложенному --apply
```

даёт `<dest>/<ИмяЧеловека>/<файл>.jpg` для каждого фото, где этот человек —
(или главный, см. `sort.multi_person` в §21) названное лицо — всему остальному без
названного человека всё равно нужно куда-то деться, поэтому такие фото уходят в
`_Неразобрано/`. Маршрутизация junk/скриншотов и `--where`/`--copy`/`--move`/`--apply`
работают точно так же, как в примерах city/event выше.

## 10. Дубликаты

- **Точные дубли** (идентичные байты) находятся при `index`; сортируется только
  канонический экземпляр, остальные остаются на месте.
- **Почти‑дубли** (визуально похожие, разного размера/имени) — через перцептивные хэши
  (`sorta phash`, затем `sorta dupes --near` или вкладка **Дубли** в UI).

Во вкладке **Дубли**: у каждой группы рекомендованный кадр (★). Поправьте radio, где не
согласны, отметьте *«не удалять эту группу»* для пропуска, затем один раз нажмите
**Сохранить весь выбор** (без покадрового клика). При следующей сортировке/копии
не‑keeper'ы уйдут в папку `_удалить` (восстановимо) — либо кнопкой **Удалить** на кадре /
**Удалить дубли** отправьте их сразу в корзину ОС.

Реальный вывод на синтетической коллекции из §7 (после `sorta phash`):

```
$ sorta dupes -c config.yaml
paris_01_copy.jpg
  -> дубликат paris_01.jpg

Всего: 1

$ sorta dupes --near -c config.yaml
Группа из 2 похожих:
  paris_02.jpg  (7424 байт)
  paris_02_edited.jpg  (5908 байт)
Группа из 2 похожих:
  person_a_1.jpg  (14742 байт)
  person_a_2.jpg  (14742 байт)

Групп: 2 (порог Хэмминга: 5)
```

`paris_02_edited.jpg` — реально пересжатая/уменьшенная копия `paris_02.jpg`, ровно
случай «то же фото, отредактировано или переэкспортировано», для которого и нужен
перцептивный хэш. Вторая группа — ложное, но поучительное срабатывание: два наших
фото‑заглушки байт‑в‑байт идентичны (сгенерированы одной процедурой), поэтому pHash
корректно называет их почти‑дублями, хотя `sorta faces` считает их несвязанными
файлами (лиц не найдено ни на одном). На реальной коллекции два разных фото одного
человека обычно НЕ будут почти‑дублями — pHash сравнивает похожесть всего кадра, а
не личность.

## 11. Люди и кластеры лиц

Детекция лиц даёт **кластеры** (группы одного лица). Чтобы person‑сортировка была
осмысленной, назовите кластеры:

- **UI → вкладка Люди:** у кластера видны образцы лиц; введите имя и нажмите
  **Назвать**; выберите два кластера и **Слить**, если это один человек.
- **CLI:** `sorta faces label <cluster_id> "Мама"`, `sorta faces merge <src> <dst>`,
  `sorta faces sheet <cluster_id> out.html` (контактный лист для опознания).

После именования `sorta sort --by person` (или person‑**альбом**, §13) использует имена.

`sorta faces` нужен флаг `--faces` у `sorta run` / чекбокс «Разбор по лицам» в UI
(§8) — на базовом пайплайне он не запускается. Реальный вывод на синтетической
коллекции из §7:

```
$ sorta faces -c config.yaml
Детекция: 12 файлов, 0 лиц, 12 без лиц, 0 ошибок
Кластеры: 0 (лиц в кластерах: 0, шум: 0, имён сохранено: 0)
```

Действительно ноль — buffalo_l обучена на настоящих фотографиях и корректно не
срабатывает на наших синтетических заглушках (плоские векторные фигуры, не реальная
текстура лица). Это ожидаемо, не баг Sorta и не баг этого руководства: направьте
`sorta faces` на настоящую фотоколлекцию — и он найдёт реальные лица. Когда найдёт
(реальный, не этот синтетический прогон напечатал бы что-то вроде `Детекция: 340
файлов, 512 лиц, 8 без лиц, 0 ошибок` / `Кластеры: 6 (лиц в кластерах: 480, шум: 32,
имён сохранено: 0)`), именование и сортировка — те же команды выше:
`sorta faces label 3 "Мама"` называет кластер `3`, затем
`sorta sort --by person --dest … --apply` раскладывает фото этого человека в
`<dest>/Мама/`.

## 12. События

События группируют фото по разрывам времени и городу. `sorta events` (пере)строит их:

- Мелкие группы (меньше `events.min_event_size`) событиями не становятся.
- Сессии одного города в пределах `events.trip_merge_gap_hours` сливаются в поездку.
- Имя = диапазон дат + локализованный город (напр. `2023-11-29..12-02 Сочи`).

Ручное управление:
- `sorta events add "Конференция" 2025-05-21 2025-05-23` — ручное событие на диапазон
  дат (переживает пересчёт).
- `sorta events rename <event_id> "IEEE конференция Токио"` — ручное имя.

`sorta events` нужен флаг `--events` у `sorta run` / чекбокс «Разбор по событиям» в
UI (§8). Реальный вывод на синтетической коллекции из §7 (7 парижских файлов
проходят порог `min_event_size` по умолчанию — 5; токийский день из 4 файлов — нет):

```
$ sorta events -c config.yaml
События: 1 авто (7 файлов, имён сохранено: 0), 0 ручных (0 файлов)
```

## 13. Альбомы

**Альбом** собирает конкретный срез — одного человека (опционально с фильтром) или одно
событие — в отдельную именованную папку, не трогая каноническую структуру по городам.

```bash
# Все фото «Мама», жёсткими ссылками (по умолчанию), сначала превью, затем apply:
sorta album person "Мама" --dest /путь/к/альбомам
sorta album person "Мама" --dest /путь/к/альбомам --apply

# «Мама», но только в Барселоне:
sorta album person "Мама" --where "city=Barcelona" --dest /путь/к/альбомам --apply

# Конкретное событие с своим именем папки, копиями:
sorta album event "2025-05-21..05-23 Tokyo" --dest /путь/к/альбомам \
      --name "IEEE конференция Токио" --copy --apply
```

- Режим по умолчанию — **link** (hardlink, ~0 лишнего места; фото может быть в
  нескольких альбомах *и* в структуре по городам).
- **`--copy`** — независимые копии; **`--move`** *изымает файлы из общего пула*
  (печатает предупреждение). Фото с **2+ названными людьми** нельзя move в один альбом
  (неоднозначно) — такие блокируются; используйте link/copy.
- В UI — кнопка **Собрать в папку** на карточках Люди/События.

Реальный вывод — собираем парижское событие из §12 в альбом, копиями:

```
$ sorta album event "2023-06-10..06-11 Paris" --dest albums --copy --apply -c config.yaml
album event '2023-06-10..06-11 Paris' --apply [copy]: 7 файлов -> …\albums\2023-06-10..06-11 Paris
Альбом «2023-06-10..06-11 Paris»: выгружено 7, ошибок 0. Откат: sorta undo

$ find albums -type f
albums/2023-06-10..06-11 Paris/paris_01.jpg
albums/2023-06-10..06-11 Paris/paris_02.jpg
albums/2023-06-10..06-11 Paris/paris_02_edited.jpg
albums/2023-06-10..06-11 Paris/paris_03.jpg
albums/2023-06-10..06-11 Paris/paris_04.jpg
albums/2023-06-10..06-11 Paris/paris_05_nogps.jpg
albums/2023-06-10..06-11 Paris/person_a_1.jpg
```

Поскольку передан `--copy`, это независимые файлы — `sorta undo` здесь удаляет
только копии в альбоме, оригиналы не трогает (см. §15).

## 14. Мусор, скриншоты и документы

`sorta junk` классифицирует каждое фото, чтобы сортировка убрала не‑воспоминания из
папок городов/людей/событий:

- **`screenshot`**, **`meme`** → `_Неразобрано/junk/…`. Файлы в папке `Screenshots/`
  распознаются и по имени папки.
- **`document`** (паспорта, чеки, бланки, медицинские бумаги…) → `_Документы/` —
  **review‑папка**, *не* мусор. Детекция сочетает CLIP с сигналом **плотности текста**
  (документы плотно покрыты текстом; пляжи и товарные кадры — нет).
- **`product`** (вещь, снятая на продажу: карточка товара, кадр для маркетплейса) →
  `_Товары/` — тоже **review‑папка**, не мусор и не память. Этот класс выдаёт **только
  глубокий VLM‑ярус** (§8): быстрый ярус его не производит вовсе, там такие кадры
  остаются `photo` или попадают в `_Документы/`. На боевой коллекции это каждый
  десятый кадр — 2 202 из 24 196.

`_Документы/` намеренно **over‑собирает** (реальное фото оттуда легко вытащить; реальный
документ, утёкший в память по городам — хуже). Разбирайте вручную.

Разбирать эти корзины удобнее из веб‑интерфейса: вкладка **«Не личные фото»** (§6)
показывает их рядом, возвращает отмеченные кадры в обычную раскладку пачкой и **не
рисует миниатюры для документов** — намеренно, потому что в этой корзине лежат
персональные бумаги.

> **Приватность:** документы могут содержать персональные данные. Sorta обрабатывает их
> **локально** и никогда не отправляет наружу (если вы не включили онлайн‑провайдер).
> См. §15.

Реальный вывод на синтетической коллекции из §7 — единственное фото, сохранённое в
`Screenshots/`, распознаётся эвристикой по имени папки, остальные классифицируются
как обычные фото:

```
$ sorta junk -c config.yaml
Классификация: 12/12 обработано (photo: 11, screenshot: 1)
```

## 15. Безопасность, откат и приватность

- **Dry‑run по умолчанию** — ничего не двигается до `--apply`.
- **Сводка перед стартом (веб‑интерфейс)** — кнопка раскладки сначала показывает
  диалог с числами: куда, перемещение или копирование, сколько файлов в скольких
  папках и какого объёма, сколько из них уже лежит в назначении, сколько уедет в
  `_Товары/` и `_Документы/`. Пустой план так и говорит, что раскладывать нечего.
- **Кнопка «Отменить» во время прогона** — раскладку можно остановить, не дожидаясь
  конца: текущий файл дописывается целиком, остальные не трогаются, и в итоге
  печатается, сколько успело разложиться. Откат разложенного — на вкладке
  «Перемещения».
- **Журнал перемещений** — каждая операция записывается *до* выполнения.
- **Откат** — `sorta undo` откатывает последний батч (`--batch <id>` для конкретного).
  Для copy/link‑батчей undo удаляет копии/ссылки, а не оригиналы. В веб‑интерфейсе то
  же самое делает кнопка **«Откатить»** на вкладке **«Перемещения»** — с
  подтверждением, прогрессом и собственной кнопкой отмены; прерванный откат
  продолжается повторным нажатием.
- **Повторный запуск не плодит дубли** — вторая раскладка в тот же каталог узнаёт
  файлы, скопированные предыдущей (сверка по содержимому, а не по имени), и
  пропускает их вместо того, чтобы положить рядом копию с суффиксом `_1`. Суффикс
  остаётся там, где он и должен быть: у *другого* файла с тем же именем.
- **Сверка хэшей, без перезаписи** — blake3 проверяется перед перемещением; конфликт
  имён → `_1`, `_2`.
- **Оригиналы не тронуты с copy/link.** С move файлы переезжают, но содержимое и EXIF
  неизменны.
- **Локально по умолчанию.** Модели лиц/сцен/текста работают на вашей машине.
  Онлайн‑провайдеры — **opt‑in** в `config.yaml`: `geo.provider: online` (Nominatim)
  отправляет только GPS‑координаты, никогда не изображения; `naming.provider: claude`
  отправляет несколько фото‑образцов события в Claude API (единственная функция,
  реально покидающая машину с фото) — что именно отправляет каждый провайдер, см.
  [SECURITY.md](../../SECURITY.md). Для максимальной приватности держите их
  выключенными.
- Веб‑интерфейс слушает только `127.0.0.1`.

## 16. Полный справочник команд

```
sorta index [DIR]                 Сканировать sources (или DIR) → метаданные, хэши, точные дубли
sorta index --refresh-exif        Перечитать метаданные уже проиндексированных файлов (§17)
sorta run [--src DIR] [--faces] [--events] [--deep/--no-deep] [--geo offline|online]
          [--by city|person|event] [--dest DIR]
                                  Базовый пайплайн (index→geo→landmarks→junk); --src
                                  переопределяет config sources на этот прогон; --faces/
                                  --events включают долгие этапы (по умолчанию выкл,
                                  независимо друг от друга); --deep/--geo override
                                  config.yaml только на этот прогон; с --by в конце
                                  печатает dry-run план
sorta geo                         Определить места (GPS + наследование по сессиям)
sorta landmarks                   Визуальное место для сцен без GPS (консервативно)
sorta faces                       Детекция лиц + кластеризация людей
sorta faces label <cluster> <name>    Назвать кластер
sorta faces merge <src> <dst>          Слить два кластера (один человек)
sorta faces sheet <cluster> <out.html> Контактный лист для опознания
sorta events                      (Пере)построить события
sorta events add <name> <from> <to>    Ручное событие на диапазон дат
sorta events rename <id> <name>        Ручное имя события
sorta junk                        Классификация photo/screenshot/meme/document/product
sorta phash                       Перцептивные хэши (для почти‑дублей)
sorta stats                       Покрытие индекса (GPS, источники дат, дубли)
sorta dupes [--near]              Список точных / почти‑дублей
sorta sort --by MODE [--dest DIR] [--apply] [--copy|--move]
           [--where …] [--dedupe] [--delete-worse-dupes] [--exclude PATH] [--thumbnails]
                                  Спланировать/применить сортировку (без --apply — dry-run)
sorta album person|event <selector> --dest DIR [--copy|--move] [--where …] [--name N] [--apply]
                                  Собрать срез в именованную папку (по умолчанию hardlink)
sorta undo [--batch ID]           Откатить последний (или указанный) батч
sorta reset [--yes] [--clear-geo] Стереть индекс (БД) и начать с нуля — фото и уже
                                  разложенные папки НЕ трогает (имена людей/событий
                                  и решения по дублям при этом пропадут). Кэш
                                  онлайн‑гео переживает сброс, если не задан --clear-geo
sorta ui [--port 8756]            Локальный веб‑апп (Обработать / Города / Дубли / Люди / События / Перемещения)
sorta doctor                      Диагностика окружения: torch/onnxruntime, GPU, гео‑база,
                                  путь лога, путь кэша превью (§3.5)
sorta cache [--clear] [--clear-geo]
                                  Кэши: размер/удаление превью (§18), а --clear-geo
                                  очищает сохранённые ответы онлайн‑гео
```

Каждая команда принимает `-c/--config <path>` (по умолчанию `config.yaml`) — кроме
`sorta doctor`, который конфиг не читает вообще.

## 17. Обслуживание и диагностика

Три команды, которые не входят в пайплайн, но нужны в повседневной работе.

### `sorta doctor`

Проверка установки и окружения из §3.5: устройства torch и onnxruntime, встроенная
гео‑база, путь лога прогона и путь кэша превью. Запускайте после каждой установки и
смены профиля, а также первым делом, когда что‑то неожиданно тормозит.

### `sorta index --refresh-exif`

Перечитывает метаданные файлов, **уже находящихся в индексе**, не переиндексируя их.
Формат итоговой строки (`<N>` — счётчики вашего прогона):

```
$ sorta index --refresh-exif -c config.yaml
Перечитано: <N> файлов, обновлено <N>; вернулось координат: <N>, дат съёмки: <N>; без EXIF: <N>, ошибок: <N>
Появились новые координаты — перезапустите: sorta geo (и sorta events)
```

- **Зачем это нужно.** Обычный `sorta index` такие файлы намеренно пропускает: он
  сверяет путь + размер + mtime, а ничего из этого не менялось. Если улучшился
  *читатель* — например, обновление Sorta починило извлечение метаданных, — обычный
  прогон к ним больше никогда не вернётся.
- **Когда запускать.** После обновления, в описании которого упоминается чтение
  EXIF/метаданных, и если `sorta stats` показывает меньше файлов с GPS или
  EXIF‑датами, чем вы ожидаете.
- **Что трогает.** Только GPS, производителя/модель камеры, размеры, дату съёмки и
  ориентацию. Хеши, phash и пометки дублей **не трогаются** — содержимое файла не
  менялось, менялось лишь то, что удалось из него вычитать. Файлы целиком не
  читаются, ничего не перехэшируется.
- **Что делать после.** Новые координаты означают, что места надо определить заново:
  запустите `sorta geo`, а если вам важны события — ещё и `sorta events`. Команда
  сама напоминает об этом, когда координаты действительно вернулись.

### `sorta cache`

Показывает кэш превью (§18) или удаляет его:

```
$ sorta cache -c config.yaml
Кэш превью: C:\Users\you\AppData\Local\sorta\previews
  файлов: 34887, размер: 12.60 ГБ
  потолок: не задан (imaging.preview_cache_max_gb)

$ sorta cache --clear -c config.yaml
Кэш превью удалён: C:\Users\you\AppData\Local\sorta\previews
```

Удалять кэш безопасно в любой момент: он ленивый и пересоберётся сам, покадрово, в
той стадии, которой первой понадобится кадр. Единственная цена — эти кадры один раз
декодируются из оригиналов заново.

## 18. Кэш превью

**Что это.** Каждый кадр декодируется **один раз**. Результат — уменьшенный JPEG,
1536 px по длинной стороне — записывается в общий каталог кэша, и все последующие
стадии (pHash, CLIP, OCR, глубокий VLM‑ярус, тумбы в UI) читают эту маленькую копию
вместо повторного декода оригинала.

**Ради чего.** Именно на декод эти стадии и тратят время. Полный декод HEIC стоит
≈470 мс, тот же кадр из кэша превью — единицы миллисекунд (≈8 мс). Раньше одно и то
же фото декодировалось за прогон три‑пять раз, потому что стадии идут одна за
другой.

**Где лежит.**

| ОС | Путь |
|---|---|
| Windows | `%LOCALAPPDATA%\sorta\previews` |
| Linux / macOS | `~/.cache/sorta/previews` |

**Сколько занимает: ориентировочно 150 КБ на фото, и это гигабайты.** 150 КБ —
расчётный размер JPEG 1536 px q88; детализированные кадры получаются крупнее.
Реально измеренный здесь кэш содержал 34 887 превью на **12,60 ГБ** (≈360 КБ на
файл), так что на коллекции в десятки тысяч фото это несколько гигабайт диска, а не
погрешность. Кэш пользовательский, внутрь коллекции ничего не пишется, а текущий
размер в любой момент покажет `sorta cache` (§17).

**Мелкие изображения в кэш не попадают.** Если оригинал и так не больше
`preview_max_edge`, превью было бы копией, а не экономией, — такой файл
пропускается: коллекция из скриншотов места здесь не займёт.

**Настройка** — секция `imaging:` в `config.yaml`:

```yaml
imaging:
  preview_cache: true     # false → каждая стадия снова декодирует оригиналы
  # preview_dir: D:/sorta-previews   # по умолчанию — см. таблицу выше
  preview_max_edge: 1536  # длинная сторона кэшируемого JPEG
  preview_quality: 88     # качество JPEG в кэше
  # preview_cache_max_gb: 40   # потолок в ГБ; 0 (по умолчанию) — без потолка
```

`imaging.preview_max_edge` — длинная сторона кэшируемого JPEG; её хватает всем
потребителям с запасом (OCR берёт 1280, VLM 896, CLIP 448, pHash 96).
`imaging.preview_quality` — качество JPEG: при 88 кадр весит около 150 КБ и на этих
размерах визуально неотличим от полного декода.

У каждого ключа есть одноимённая переменная окружения — `SORTA_PREVIEW_CACHE`,
`SORTA_PREVIEW_DIR`, `SORTA_PREVIEW_MAX_EDGE`, `SORTA_PREVIEW_QUALITY`,
`SORTA_PREVIEW_MAX_GB`, — и при конфликте **выигрывает переменная**, а не
`config.yaml`.

**Потолок кэша: `imaging.preview_cache_max_gb`.** По умолчанию `0` — потолка нет,
и кэш растёт, пока на диске есть место. Это осознанный выбор: кэш окупается на
каждом полном прогоне, поэтому правильный ответ на «диск кончился» — **ограничить
кэш, а не выключить его**. Выключение вернёт декод оригинала в каждой стадии, то
есть 336 мс на кадр вместо 73.

Когда потолок задан и кэш в него не влезает, удаляются превью, **которые дольше
всего не читали**, — и ровно столько, чтобы уложиться в лимит. Не самые старые:
превью, к которому продолжают обращаться следующие стадии, дешевле сохранить, чем
декодировать заново. Каталог целиком при этом не чистится — единственная причина
удалить файл в том, что общий объём не помещается.

Проверка объёма делается **не на каждой записи**, а раз в 512 превью: она обходит
весь каталог, а это десятки тысяч файлов. Между проверками кэш может превысить
лимит примерно на 75 МБ — величина, незаметная на фоне любого осмысленного потолка.

Ориентир для выбора числа: ≈150 КБ на фото, то есть ~45 ГБ на 300 тысячах кадров и
~75 ГБ на полумиллионе. Текущий размер и потолок печатает `sorta cache` (§17); то же
самое показывает вкладка «Обработать» в `sorta ui`, а поменять значение можно прямо
в колонке настроек — без перезапуска.

**Видео тоже попадает в этот кэш.** Из клипа извлекается кадр и кладётся рядом с
превью фотографий: 68% видео реальной коллекции оказались в HEVC, который браузер не
проигрывает, поэтому кадр — единственное, что показывается везде одинаково. Ни одна
стадия пайплайна видео не декодирует — эти превью нужны только интерфейсу.

```yaml
imaging:
  # video_previews: true   # false → у клипов не будет плитки в UI
  # video_workers: 4       # потоков извлечения кадров
  # video_frames: 6        # кадров в «плёнке» лайтбокса; 1 → одна плитка, как было
```

`imaging.video_previews` включает эти плитки целиком, `imaging.video_workers` задаёт
число потоков извлечения, а `imaging.video_frames` — это лента кадров в лайтбоксе:
один кадр говорит, что это за клип, а шесть — ваш ли он и где снят. Лента строится за
один проход и только когда лайтбокс действительно открыли. Переменные окружения —
`SORTA_VIDEO_PREVIEWS`, `SORTA_VIDEO_WORKERS`, `SORTA_VIDEO_FRAMES`.

## 19. Лог прогона

От долгого прогона на консоли не остаётся ничего — а `sorta ui` вообще живёт часами
в фоновом окне, куда никто не смотрит. Поэтому каждая команда пишет ещё и файл лога.

| ОС | Путь |
|---|---|
| Windows | `%LOCALAPPDATA%\sorta\logs\sorta.log` |
| Linux / macOS | `~/.cache/sorta/logs/sorta.log` |

Ротация — **5 МБ, 5 файлов** (`sorta.log.1` … `sorta.log.5`), так что бесконечно он
не растёт. Прогон пайплайна (`sorta run`) и каждый старт `sorta ui` дополнительно
пишут заголовок окружения (версии Sorta и Python, платформа, откуда импортирован
пакет `sorta`, состояние GPU, гео‑данные, рабочий каталог) — то же, что печатает
`sorta doctor`, но зафиксированное на момент прогона.

**Тайминги стадий.** Каждая стадия прогона пайплайна (`sorta run` или кнопка
«Обработать» в UI) пишет пару машиночитаемых строк стабильного вида
`stage=<имя> … elapsed=<секунды>`, так что профиль прогона читается без разбора
прозы. Реальный профиль прогона от 2026‑07‑25:

```
2026-07-25T23:37:10.345 INFO sorta.runlog [Thread-23 (_run_pipeline)] stage=index started
2026-07-25T23:37:43.854 INFO sorta.runlog [Thread-23 (_run_pipeline)] stage=index elapsed=33.509
2026-07-25T23:37:43.855 INFO sorta.runlog [Thread-23 (_run_pipeline)] stage=geo started
2026-07-25T23:37:47.727 INFO sorta.runlog [Thread-23 (_run_pipeline)] stage=geo elapsed=3.872
2026-07-25T23:37:47.727 INFO sorta.runlog [Thread-23 (_run_pipeline)] stage=landmarks started
2026-07-25T23:41:34.228 INFO sorta.runlog [Thread-23 (_run_pipeline)] stage=landmarks elapsed=226.501
2026-07-25T23:41:34.229 INFO sorta.runlog [Thread-23 (_run_pipeline)] stage=junk started
2026-07-26T00:10:34.736 INFO sorta.runlog [Thread-23 (_run_pipeline)] stage=junk elapsed=1740.508
2026-07-26T00:10:34.736 INFO sorta.runlog [Thread-23 (_run_pipeline)] stage=phash started
2026-07-26T00:26:09.900 INFO sorta.runlog [Thread-23 (_run_pipeline)] stage=phash elapsed=935.164
```

Читается сразу: `junk` занял 29 минут, `phash` — 15,6, вдвоём это 91 % от 49‑минутного
прогона, а `index` (33 с) и `geo` (4 с) — шум. Именно туда имеет смысл направлять установку с
экстрой `gpu`, `naming.clip.decode_workers` или `naming.ocr_workers` (§21). По этим
же строкам отличают «зависло» от «идёт долгая стадия».

Другие формы той же строки: `stage=<имя> failed elapsed=…` (следом — traceback) и
`stage=<имя> interrupted (…) elapsed=…` для отменённого прогона — нажатая в UI
кнопка «Отмена» не ошибка. Стадия, которая сообщает счётчик, добавляет ещё
` processed=<n> rate=<n>/s`.

**Переопределения.**

- `SORTA_LOG_FILE=<путь>` — писать лог в другое место.
- `SORTA_LOG_LEVEL=DEBUG|INFO|WARNING|ERROR` — уровень **файлового** приёмника (по
  умолчанию `INFO`).

Уровень файла независим от консольного: `log_level` в `config.yaml` управляет только
тем, что печатается в консоль (по умолчанию `WARNING` — предупреждения и ошибки), а
в файле остаётся подробность уровня `INFO`, включая тайминги стадий. Тихая консоль
не делает лог‑файл тихим.

## 20. Офлайн-режим моделей

ML‑модели (CLIP, easyocr и VLM‑ярус, если вы им пользуетесь) скачиваются **один
раз**. Дальше сеть для них не нужна вообще — именно так и должен выглядеть принцип
«локально по умолчанию» на практике.

Переключение автоматическое: как только в кэше Hugging Face есть хотя бы одна
скачанная модель, Sorta стартует каждую команду с включённым офлайн‑режимом
(`HF_HUB_OFFLINE` / `TRANSFORMERS_OFFLINE`), и ни одна стадия не ходит на Hub
сверять ревизию весов, которые уже лежат на диске. Свежая машина с пустым кэшем не
трогается — первое скачивание по‑прежнему работает.

- `SORTA_ALLOW_MODEL_DOWNLOAD=1` **отключает** автопереключение — это то, что нужно,
  когда надо дотянуть *новую* модель на машине, где другие уже закэшированы
  (например, впервые включаете VLM‑ярус).
- Если вы сами задали `HF_HUB_OFFLINE` или `TRANSFORMERS_OFFLINE`, Sorta ваше
  значение не переопределяет.

Детекция лиц (insightface/`buffalo_l`) держит собственный кэш в
`~/.insightface/models` и на эти переменные не реагирует.

## 21. Справочник конфигурации

Ключевые секции `config.yaml` (полный шаблон — в `config.example.yaml`):

```yaml
sources: ["D:/Photos"]         # папки для сканирования (рекурсивно)
database: "sorta.db"           # путь SQLite‑индекса
language: ru                   # ru | en | ja — язык папок, UI и сообщений CLI (по умолчанию en)

index:
  min_file_size_kb: 5          # игнорировать крошечные файлы
  workers: 8                   # параллельное хэширование
  exif_workers: 8              # параллельные сессии exiftool (0/нет = авто min(8, ядер))
  skip_dirs: [".thumbnails", "@eaDir", "$RECYCLE.BIN", "System Volume Information"]

geo:
  provider: offline            # offline (bundled GeoNames) | online (Nominatim/OSM)
  session_gap_hours: 6         # разрыв, разделяющий сессии гео‑наследования
  nominatim_url: "https://nominatim.openstreetmap.org"   # только при provider: online
  nominatim_user_agent: "sorta-photo-organizer"          # обязателен политикой OSM
  cache_max_age_days: 180      # срок годности сохранённого онлайн-ответа (0 — бессрочно)

events:
  gap_hours: 6                 # разрыв, начинающий новую сессию
  trip_merge_gap_hours: 48     # сессии одного города в пределах — в одну поездку
  min_event_size: 5            # меньшие группы не становятся событиями

sort:
  multi_person: primary        # фото с несколькими людьми → человек крупнейшего лица
  exclude_dirs: []             # подпапки, пропускаемые при сортировке
  album_dir: null              # корень альбомов (по умолчанию _Альбомы рядом с базой)
  report_dir: null             # куда пишутся планы sort (CSV/HTML) (по умолчанию report_output/ рядом с базой)

faces:
  min_face_px: 40              # игнорировать лица мельче
  det_threshold: 0.7           # уверенность детектора
  min_cluster_size: 5          # минимум лиц в кластере (HDBSCAN)
  max_distance: 0.5            # порог косинусного сходства

naming:
  landmark_threshold: 0.85     # порог CLIP для визуального места (консервативно)
  junk_threshold: 0.85         # порог CLIP для screenshot/meme
  document_threshold: 0.9      # порог CLIP для документов
  text_frac_document: 0.15     # доля площади под текстом, выше которой фото → документ
  text_rescue_docscore_min: 0.3  # OCR‑рескью только для фото с doc‑score ≥ этого
  ocr_workers: 4               # параллельные OCR‑детекторы (по умолчанию min(4, ядер))
  product_candidate_min: 0.4   # product‑CLIP выше этого → кадр уходит в VLM‑ярус
  clip:
    batch_size: 16             # размер батча CLIP на GPU
    decode_workers: 0          # потоки декода для CLIP; 0 = авто min(ядер, 16)

vlm:                           # рантайм локальной VLM — общий для junk и имён событий
  enabled: false               # глубокий VLM‑ярус классификации (нужна экстра `vlm`);
                               #   то же, что `--deep` / чекбокс «Глубокий анализ» в UI
  model: "Qwen/Qwen2.5-VL-3B-Instruct"
  workers: 4                   # потоки подготовки кадров (по умолчанию min(4, ядер))
  max_edge: 896                # длинная сторона кадра, который видит модель

imaging:                       # кэш превью — см. §18
  preview_cache: true
  preview_max_edge: 1536
  preview_quality: 88
  preview_cache_max_gb: 0      # 0 = без потолка; иначе — вытеснение до лимита

log_level: WARNING             # только консоль; лог прогона остаётся на INFO (§19)
```

### Полный список ключей

Выше — то, что меняют чаще всего. Ниже — все остальные, по секциям. Значение по
умолчанию указано то, которое действует, если ключа в `config.yaml` нет вовсе.

**`index:` — что попадает в индекс**

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `index.extensions` | три списка: `photo`, `raw`, `video` | Какие расширения считаются фото, RAW и видео. Файл с расширением не из списков не индексируется вообще. |
| `index.min_file_size_kb` | `5` | Файлы мельче пропускаются — это иконки и артефакты, а не снимки. |
| `index.compute_phash` | `true` | Считать ли pHash сразу в `index`. При `false` почти‑дубликаты появятся только после отдельного `sorta phash`. |
| `index.phash_max_distance` | `5` | Порог Хэмминга, ниже которого два кадра считаются почти‑дубликатами (§10). |
| `index.skip_dirs` | `.thumbnails`, `@eaDir`, `$RECYCLE.BIN`, `System Volume Information` | Служебные папки, в которые обход не заходит. Про исключение **своих** папок — §21a. |

**`dedup:` — какой файл группы дублей главный**

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `dedup.canonical_strategy` | `prefer_exif_then_largest` | Из точных дублей каноническим становится файл с EXIF, а при прочих равных — больший. Остальные помечаются дублями и в раскладку не идут. |
| `dedup.keeper_vlm` | `false` | Спрашивать локальную VLM, какой кадр группы почти-дублей стоит оставить, — один сравнительный вопрос («какой из этих лучше») на группу, а не оценка каждого кадра по отдельности. Модель видит то, чего не видит резкость: закрытые глаза, отвёрнутое лицо, руку перед объективом. Нужен установленный extra `vlm`; ответ записывается в таблицу `group_keeper` как **рекомендация** вместе с её источником (`sharpness` или модель), и ничего не удаляет, не перемещает и не помечает — решение о дубле остаётся за вами. С выключенным ключом вкладка «Дубли» рекомендует по резкости, как и раньше. |
| `dedup.keeper_max_frames` | `5` | Сколько кадров группы уходит в этот вопрос — лучшие N по резкости; остальные модели не показываются, а ответ применяется ко всей группе. Группы в несколько десятков кадров встречаются, а 3B-модель, которой предложили сравнить 38 картинок, не даёт осмысленного ответа. |
| `dedup.keeper_min_group_size` | `2` | Минимальный размер группы, о которой вообще спрашивают модель. `2` — все группы; поставьте `3`, чтобы платить только там, где выбор действительно неочевиден: на **паре** кадров одной сцены резкость уже сравнивает их честно, а пары — подавляющее большинство групп (на эталонной коллекции 791 группа, из них 115 — от трёх кадров). |

**`geo:` — как определяется место**

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `geo.session_gap_hours` | `6` | Разрыв во времени, разделяющий съёмочные сессии. Внутри сессии кадр без GPS берёт место у соседей по времени. |
| `geo.nominatim_url` | `https://nominatim.openstreetmap.org` | Адрес онлайн‑геокодера. Свой сервер снимает и лимит скорости, и вопрос приватности. |
| `geo.nominatim_user_agent` | `sorta-photo-organizer` | Требование политики OSM: публичный сервис отвергает запросы без внятного User‑Agent. |
| `geo.nominatim_timeout` | `10` | Таймаут одного запроса к геокодеру, секунды. |

|---|---|---|

| `features.pet_threshold` | `0.7` | Порог уверенности. **Замерен** на 320 размеченных вручную кадрах, выборка по полосам оценки со взвешиванием обратно к коллекции: при `0.7` помечается 805 кадров с точностью 92% и полнотой 54%; при `0.6` было 895 кадров, 89% и 58%. Поднимать выше смысла нет — `0.85` даёт ту же точность при полноте на девять пунктов ниже. Оценки хранятся, поэтому смена порога не требует нового прогона. |
| `features.pets_verify` | `false` | Проверять ли каждого кандидата **локальной VLM** перед тем, как поставить метку животного: один вопрос с тремя ответами — живое животное, изображение животного (рисунок, игрушка, принт, статуя) или животного нет. Нужен включённый `features.pets` (проверка подтверждает найденное CLIP, сама не ищет), а веса — те же, что у всей секции `vlm:`, вторая модель не поднимается. Смысл в том, что ошибки, оставшиеся при точности 92%, порогом не убираются: CLIP сравнивает картинку с текстом целиком и не отличает кошку от изображения кошки. Ответ модели перекрывает оценку — кадр с оценкой 0.95 и ответом «плюшевая игрушка» не животное, — а кадр, о котором модель не ответила или до которого не дошла, сохраняет ровно ту метку, которую даёт `features.pet_threshold`. | `features.pet_candidate_threshold` | `0.5` | Кого показывать модели при включённом `features.pets_verify` — второй, гораздо более низкий порог. `0.7` выше высок именно потому, что ответ CLIP никто не проверял; когда проверяющий появился, отбор можно опускать — там и лежит недостающая полнота (около 466 животных сидят ниже `0.3`). Посчитано по хранимым оценкам коллекции в 19 757 фотографий при замеренных 0.78 с на кадр: `0.7` отбирает 805 кадров (10,5 мин), `0.5` — 993 (12,9 мин), `0.3` — 1 331 (17,3 мин), `0.2` — 1 679 (21,8 мин), всё подряд — 19 757 (4,3 часа). При выключенной проверке не используется. |
| `features.landmarks_verify` | `false` | Проверять ли **локальной VLM каждую достопримечательность, которую предложил CLIP**, прежде чем записать место: модель спрашивают, какое известное место на снимке, и дальше идёт только то предложение, которое она назвала сама. Порядок не гнётся — CLIP предлагает, модель проверяет, решает корроборация за `naming.landmark_threshold`; согласие двух моделей никогда не перекрывает страну, названную в пути. Смысл в том, что провал CLIP здесь не в восприятии, а в знании: неправильные города набирали 0.980 против 0.991 у правильного, и ни один порог их не разделяет. Поэтому фичу сначала замерили, а потом построили. На 104 кадрах с известным ответом — из них 24 предложения, в которые CLIP поверил, а корроборация отвергла, — модель подтвердила неправильный город ноль раз при точности 92%: не потому, что знает все места, а потому, что молчит, когда не знает (71 ответ из 104 не назвал ничего). Нужен extra `[vlm]`; если веса не поднялись, прогон ведёт себя ровно как с выключенным тумблером, а с выключенным — не меняется ни в чём. |
| `features.landmark_candidate_threshold` | `0.5` | Кого показывать модели при включённом `features.landmarks_verify` — второй, гораздо более низкий порог, ровно как в паре выше. `naming.landmark_threshold` высок именно потому, что предложение CLIP никто не проверял; когда проверяющий появился, отбор можно опускать. Замерено на 7 619 кадрах без места живой коллекции: `0.85` даёт 10 предложений (8 оставит корроборация, 2 отвергнет), `0.7` — 66 (52 / 14), `0.5` — 151 (127 / 24). 151 вопрос — это пара минут VLM. | `features.sharpness_max_edge` | `512` | До какого размера ужимается превью перед оценкой резкости (дисперсия лапласиана). |

| `features.subject_score_min` | `0.9` | Порог «в кадре есть осмысленный объект» — им отсекаются случайные снимки из кармана. |
| `features.blur_review_max` | `90.0` | Докуда по умолчанию открывается список нерезких кадров для просмотра. **Это не вердикт «размыто».** Замер говорит обратное: при осмотре полосами размытые кадры нашлись в **каждой** полосе вплоть до 400 — резкость ранжирует, но не классифицирует, и никакая граница не отделяет брак от мягкого, но нужного снимка. Полосы показали другое: отдача падает около 90–120 (ниже 70 — 378 кадров, ниже 90 — 530, ниже 120 — 785, ниже 160 — 1215 на коллекции в 19 757 фото). Пользователю он ничего не показывает: он нужен, чтобы будущая фича — поиск словами, альбом по запросу, «похожие кадры» — работала без нового прохода CLIP по всей коллекции. Включено по умолчанию: цена мала (~60 МБ на 20 000 фото, запись внутри уже идущего прохода), а выключенное состояние — это то, где каждая такая фича стоит полного прохода. Выключайте на очень больших коллекциях: 300 000 фото — это ~920 МБ. Векторы хранятся L2-нормализованными в float32 вместе с моделью, которая их посчитала: смените `naming.clip.model` или `naming.clip.pretrained` — и строки пересчитаются, а не будут использованы, потому что векторы разных моделей несравнимы. |
| `features.search_limit` | `200` | Сколько кадров берёт поиск словами: `sorta search "торт"` печатает столько, `sorta album query "торт" --dest …` столько собирает. **Не порог похожести**, и его здесь не будет — по той же причине, по которой его нет у резкости: оценка CLIP упорядочивает кадры относительно друг друга и ничего не значит в абсолютных числах, так что черту «это точно торт» провести нельзя. Нужен `features.store_embeddings`. |

### Секция `vlm:`

Всё, что описывает **сам рантайм локальной модели**, живёт в секции `vlm:` — её
используют оба потребителя: глубокий ярус классификации junk (§14) и провайдер имён
событий `naming.provider: vlm` (§12). Веса одни и те же, одна копия на процесс, поэтому
и настройки общие.

| Ключ | Что делает |
|---|---|
| `vlm.enabled` | Включает глубокий ярус в конфиге насовсем. По умолчанию `false`. На один прогон то же самое делают `--deep`/`--no-deep` и чекбокс «Глубокий анализ (VLM)» в веб‑интерфейсе. Без экстры `vlm` прогон аккуратно откатывается на быстрый CLIP‑ярус. |
| `vlm.model` | Идентификатор модели. По умолчанию `Qwen/Qwen2.5-VL-3B-Instruct`. |
| `vlm.workers` | Потоки, готовящие кадры (декод + препроцессинг), пока GPU считает предыдущий. По умолчанию `min(4, ядер)`. На вердикты не влияет — метки применяются в порядке кандидатов при любом значении. |
| `vlm.max_edge` | Длинная сторона кадра, до которой он ужимается перед моделью, — главный рычаг стоимости яруса. По умолчанию `896`. Уменьшать не бесплатно: документы опознаются по мелкому тексту. |
| `vlm.quality` | Отдельный тоггл вопросов о качестве кадра: открыты ли глаза, есть ли внятный сюжет. По умолчанию `false`. Третий вопрос — «не случайный ли снимок» — задавался до F122 и убран: на размеченной выборке он оказался верен в 5% случаев, то есть был чистым шумом. Ответ про глаза принимается только там, где детектор лиц нашёл лицо. Резкость и животные считаются без него — лапласианом и CLIP‑ом, это бесплатно; модель спрашивают только о том, чего они не решают. |
| `vlm.quality_scope` | Кого спрашивать: `groups` (кадры групп почти‑дублей, по умолчанию), `events` (плюс выборка кадров каждого события), `all` (все живые фото). `all` на 20 тысячах кадров — это часы GPU, поэтому дефолт узкий. |
| `vlm.exclude_classes` | **Приватность:** классы, которые модель не видит никогда. По умолчанию `[document]` — эта корзина содержит паспорта, медбланки и справки, а проект уже отказывается их декодировать для показа. Модель локальная, наружу ничего не уходит, но решение ваше. **Цена реальна:** именно глубокий ярус *исправляет* ошибочный вердикт «документ» (на живом прогоне пляжное фото получило 0.95 как документ), поэтому исключённый класс остаётся с тем, что решил быстрый ярус. Допустимы `document`, `product`, `screenshot`, `meme`; `[]` — показывать всё. `photo` исключить нельзя. |

> **Старый конфиг менять не обязательно.** Прежние адреса `naming.vlm_enabled`,
> `naming.classify_vlm_model` и `naming.vlm_workers` **читаются по-прежнему** и
> работают как алиасы для `vlm.enabled` / `vlm.model` / `vlm.workers`. Если ключ задан
> в обоих местах — выигрывает `vlm:`; если только по старому адресу, Sorta один раз за
> прогон пишет предупреждение вида `config: ключ naming.vlm_enabled устарел —
> переименуйте его в vlm.enabled (пока читается по-старому)`. Это предупреждение, а не
> ошибка: ничего не сломалось, переименовать можно когда удобно. У `vlm.max_edge`
> старого адреса нет — раньше это была константа в коде.

### Параметры пропускной способности

Скорость тяжёлых стадий определяют четыре ручки. Все они необязательные — значения
по умолчанию выбраны так, чтобы не завалить скромное железо, а подробные комментарии
и замеры уже есть в `config.example.yaml`.

| Параметр | Что делает | Когда трогать |
|---|---|---|
| `index.exif_workers` | Параллельные сессии `exiftool` на стадии `index`. exiftool — отдельный процесс, поэтому масштабируется почти линейно (замер: 11,8 → 2,0 мс на файл при переходе с 1 на 8 сессий). По умолчанию авто, `min(8, ядер)`. | Поднять на многоядерной машине, если в логе доминирует `stage=index`. |
| `naming.ocr_workers` | Параллельные OCR‑детекторы в `junk`. Каждый воркер держит **свою** копию модели в VRAM, поэтому по умолчанию значение намеренно скромное: `min(4, ядер)`. | Поднимать только при запасе VRAM; понижать, если именно OCR упирается в память. |
| `naming.clip.batch_size` | Размер батча CLIP на GPU. Путь CLIP упирается в декод, так что влияние минимально. По умолчанию 16. | Менять почти никогда не нужно. |
| `naming.clip.decode_workers` | Потоки декода, кормящие CLIP, — главный рычаг скорости `junk`/`landmarks`. По умолчанию авто, `min(ядер, 16)`. | Поднять, если доминируют `stage=junk`/`stage=landmarks`, а GPU простаивает. |

## 21a. Пропуск папок и ручная правка раскладки

Две разные задачи и два разных инструмента. Их легко перепутать, поэтому формулировки
выбраны намеренно:

- **«не сканировать»** — файлы вообще не попадают в индекс;
- **«не раскладывать»** — файлы в индексе, но остаются на своих местах.

### Исключение исходных папок до сканирования

Папку источника можно исключить *до* того, как обход до неё дойдёт, — и это
единственный вариант, который экономит работу: исключённое поддерево не стоит ни
одного `stat`, ни хеширования, ни последующих стадий. На реальной коллекции в 400 ГБ
исключение одной папки `Movies` убрало 847 файлов и 54 ГБ из всех стадий прогона.

В веб-интерфейсе на первой вкладке показывается дерево папок источника. У каждой папки
три состояния: ☐ обрабатывать, ◐ не раскладывать, ☒ не сканировать — щелчок по значку
переключает их по кругу, состояние родителя действует на всё поддерево. Из командной
строки:

```bash
sorta index --exclude-dir Movies --exclude-dir Screenshots
```

Оба способа пишут в один файл — `excludes.yaml` рядом с базой либо туда, куда
указывает `index.excludes_file`, — поэтому папка, исключённая в одном месте,
остаётся исключённой и в другом. Файл группируется **по корню источника**, а внутри
корня — по смыслу исключения:

```yaml
"D:/Photos":
  skip_scan:      # не сканировать: файлов не будет в индексе
    - Movies
    - DCIM3/Screenshots
  skip_layout:    # не раскладывать: в индексе, лежат на месте
    - foto/Греция
    - foto/Франция
"E:/Archive":
  skip_scan:
    - temp
```

Папка попадает ровно в один раздел: отметка одного состояния снимает другое. Файл
старого формата (плоский список под корнем) читается как `skip_scan` — переписывать
его не нужно.

Благодаря этому смена источника не требует решать судьбу старых исключений: у каждого
корня свой набор, и при возврате он восстанавливается. Учтите: файлы, уже
проиндексированные под свежеисключённым путём, **удаляются из индекса** на следующем
запуске `index` — «не сканировать» и «есть в индексе» не могут быть верны
одновременно. Журнал перемещений при этом не трогается.

### Правка отдельных файлов

Автоматические правила не видят того, что видите вы. В веб-интерфейсе любой файл
(или выделение) можно:

- **исключить из раскладки** — он не копируется и не переносится и вовсе не
  появляется в плане;
- **перенести** — в любую папку текущей раскладки.

Обе правки сильнее любых автоматических правил: решения по дубликатам, вердикта
классификатора, гео. Они хранятся в индексе и стираются переиндексацией с нуля — так
же, как имена кластеров лиц и названия событий.

### Откуда пришёл файл

В строке файла показывается папка, из которой он взят, а полный путь — в подсказке.
Обычно это самый быстрый способ оценить неверную догадку: совпадение с Колизеем
очевидно ошибочно, когда видно, что файл лежит в папке, названной по карельскому
парку.

## 21b. Файлы без надёжной даты

Снимок, дату которого установить не удалось, не сваливается в одну кучу со скачанной
картинкой. Разделение идёт по тому, есть ли хоть какой-то след камеры (производитель,
модель или GPS):

- снимок камеры с потерянной датой — папка «без даты»;
- никаких следов камеры — папка **«скачанное»**.

На проверочной коллекции граница прошла почти идеально: из 1 059 файлов без даты у
1 057 не было следов камеры — это кэш мессенджеров с именами вида
`10083666931142353280.JPG`, — и ровно 2 оказались настоящими снимками. Название папки
намеренно не звучит как приговор: пересланные картинки часто стоит просмотреть.

## 22. Решение проблем

- **`sorta doctor` показывает `torch: 2.13.0+cpu` на машине с GPU** — экстра не
  доехала до команды установки. У `uv tool install` нет флага `--extra`; экстра
  живёт внутри закавыченной спецификации:
  `uv tool install --force "C:\path\to\sorta[gpu]"` (§3.3).
- **В `sorta doctor` нет `CUDAExecutionProvider`**, хотя torch видит CUDA — обычный
  `onnxruntime` (его тянет `insightface`) затёр `onnxruntime-gpu`, и детекция лиц
  считается на CPU. Разбор и обход — в §3.6.
- **Правки кода не дают эффекта** — не‑editable `uv tool install` это снапшот кода
  на момент установки. Переустановите с `-e` (§3.3) или используйте venv проекта
  (§3.4).
- **`uv sync` без extra оставляет `sorta faces`/`sorta junk` сломанными или
  несогласованными** — ожидаемо. Всегда ставьте с явным профилем:
  `uv sync --extra cpu --extra dev` или `uv sync --extra gpu --extra dev` (§2/§3).
  `cpu`/`gpu` взаимоисключающие; смена железа позже — просто повторный `uv sync` с
  другим extra.
- **`No module named ruff` / нет dev‑инструментов** — добавьте `--extra dev` к
  вашему `uv sync` (это отдельно от профиля cpu/gpu, см. выше).
- **Нет дат/превью/метаданных видео для HEIC/RAW** — установите `exiftool` (см. §3);
  он обязателен для этих форматов, Pillow покрывает только JPEG/PNG/TIFF/WEBP.
- **Лица/CLIP очень медленно на GPU‑профиле** — убедитесь, что реально стоял
  `uv sync --extra gpu` (не `cpu`) и что драйвер поддерживает CUDA 13; `sorta faces`/
  `sorta junk` печатают, какой execution provider onnxruntime выбрал
  (`CUDAExecutionProvider` vs `CPUExecutionProvider`) в начале вывода.
- **Классификация/лица медленные, хотя ставили `--extra gpu`** — скорее всего,
  вы запускаете `sorta` через голый `uv run sorta …`. `uv run` перед каждым
  запуском пересинхронизирует окружение под базовые зависимости из
  `pyproject.toml`, что откатывает GPU‑сборку torch на CPU, если не повторять
  `--extra gpu` на этой самой команде каждый раз (см. §3). Запускайте бинарь от
  `uv tool install` (`uv tool install ".[gpu]"`, дальше просто `sorta …`) либо
  активированный venv — ни то, ни другое не пересинкается на каждый вызов.
  Проверка GPU: `python -c "import torch; print(torch.cuda.is_available())"`
  должно напечатать `True`. Сменить профиль железа = переустановить с другим
  extra — тот же шаг, что описан в §3.
- **Намеренно форсировать CPU на GPU‑профиле** (например, для отладки, или GPU занят
  чем-то другим) — задайте `CUDA_VISIBLE_DEVICES=` (пусто) для команды; и torch, и
  onnxruntime это учитывают и откатываются на CPU:
  ```bash
  CUDA_VISIBLE_DEVICES= sorta faces          # bash/macOS/Linux
  ```
  ```powershell
  $env:CUDA_VISIBLE_DEVICES=''; sorta faces  # PowerShell
  ```
- **`buffalo_l` перекачивается заново каждый раз** — кэш модели
  (`~/.insightface/models/buffalo_l`) удалён или недоступен для записи; убедитесь,
  что этот путь (или симлинк/junction туда, где реально лежит модель) сохраняется
  между запусками.
- **`database is locked`** — другой процесс Sorta пишет (напр. прогон пайплайна).
  Дождитесь завершения; не запускайте двух писателей одновременно.
- **Во время прогона место на диске уменьшилось на гигабайты** — скорее всего это
  кэш превью (§18): ≈150 КБ на фото и больше. Посмотреть — `sorta cache`, удалить —
  `sorta cache --clear`, перенести — `imaging.preview_dir`, выключить —
  `imaging.preview_cache: false` (ценой повторного декода каждого кадра в каждой
  стадии).
- **Модель отказывается скачиваться на машине, где другие модели уже есть** —
  ожидаемо: Sorta переводит Hugging Face в офлайн, как только его кэш непустой
  (§20). Запустите команду один раз с `SORTA_ALLOW_MODEL_DOWNLOAD=1`, чтобы дотянуть
  новые веса.
- **Папка с не‑ASCII именем (напр. кириллица) как будто пропущена OCR** — исправлено:
  изображения декодируются через Unicode‑безопасный путь; обновитесь до последней
  версии.
- **`sorta --help` на английском, хотя в конфиге `language: ru`/`ja`** — ожидаемо, не
  баг: тексты справки лежат в декораторах typer и вычисляются при импорте модуля,
  раньше, чем прочитан конфиг. Всё остальное — строки прогресса, сводки команд, имена
  папок, веб‑интерфейс — говорит на языке из `language` (см. §4). Если сообщения
  печатаются на нужном языке, но превращаются в `????` в терминале — это отдельная,
  чисто косметическая проблема кодировки (следующий пункт).
- **Кириллица/японский искажаются в Windows‑консоли** — косметика; файлы и веб‑интерфейс
  не затронуты. Используйте веб‑интерфейс, UTF‑8‑терминал, либо задайте
  `PYTHONUTF8=1` перед запуском `sorta`.
- **`sorta landmarks` (или другая команда) падает с ошибкой относительного пути
  вида «`data/landmarks.yaml` не найден»** — этот путь (`naming.landmarks_file` в
  `config.yaml`) резолвится относительно **текущей директории**, а не репозитория.
  Либо запускайте `sorta` из корня репозитория, либо задайте абсолютный путь для
  `naming.landmarks_file` в своём `config.yaml`.
